Objective

Take the current experimental repository and evolve it into a tidy, understandable, moderately scalable application while preserving the working pieces that already exist.

The system should support:

Data ingestion
    ↓
Knowledge Graph + Vector Search + Keyword Search
    ↓
Agent tools
    ↓
Agent reasoning
    ↓
Backend
    ↓
Simple UI

This is still a prototype / challenge project. Prefer simplicity, clear boundaries, and working end-to-end functionality over production-scale infrastructure.

Do not rewrite working components just to make the architecture look cleaner.

Important working assumptions

The repository already contains working experiments around:

CRM CSV → RDF / Knowledge Graph
GraphDB
ontology-driven SPARQL
transcript semantic extraction into RDF
ChromaDB transcript retrieval
BM25 transcript retrieval
LLM-generated SPARQL
LLM-generated natural-language answers

Inspect the repository first and determine exactly what exists and what already works.

Treat the current repository as the source of truth. Use available conversation history as additional context, but do not assume that something exists merely because it was discussed.

The agent should choose which retrieval mechanisms to use depending on the question.

Do not hard-code a pipeline that always queries all three systems.

Examples:

"What is blocking D001?"
→ probably KG

"What exactly did the customer say about security?"
→ KG and/or transcript retrieval

"Has anyone discussed something similar to data sovereignty?"
→ semantic search, perhaps lexical search, then KG context
Main components
1. Ingestion

There should be a clear ingestion entry point.

It should orchestrate existing ingestion functionality rather than duplicate it.

Conceptually:

CRM CSV
  → RDF
  → GraphDB

Transcripts
  ├→ semantic extraction → RDF → GraphDB
  ├→ Chroma embeddings
  └→ BM25 corpus/index

Reuse existing scripts wherever possible.

Do not build a generic ETL framework.

A command such as:

python -m app.ingestion

or similarly simple entry point is sufficient.

The ingestion process should be understandable from the repository structure.

2. Knowledge Graph

GraphDB remains the structured knowledge store.

Preserve:

ontology
CRM RDF
extracted transcript facts
evidence/provenance
SPARQL access

Do not replace GraphDB.

The system should continue to support arbitrary read-only SPARQL queries generated by the agent.

3. Semantic retrieval

Use the existing Chroma implementation.

For now:

one transcript = one document

Do not introduce chunking unless there is a concrete need.

Use the existing/default embedding model for now.

The architecture should make changing the embedding model later straightforward.

4. Lexical retrieval

Use the existing BM25 implementation.

Keep it lightweight.

Do not introduce Elasticsearch, OpenSearch, or another server solely for lexical search.

MCP tool layer

Create a small MCP server that exposes retrieval capabilities to the agent.

The initial tool surface should stay narrow.

Approximately:

query_kg(sparql)

semantic_search(
    query,
    top_k=3
)

keyword_search(
    query,
    top_k=3
)

get_transcript(
    transcript_id
)

describe_kg_schema()

Tool names can change if better names already exist in the repository.

MCP responsibilities

The MCP layer is the access boundary.

It should:

expose only necessary functionality
validate arguments
enforce reasonable limits
prevent destructive operations
return structured results

For GraphDB, allow read operations only.

Reject SPARQL updates such as:

INSERT
DELETE
CLEAR
DROP
CREATE
LOAD
MOVE
COPY
ADD

Reasonable limits are sufficient, for example:

SPARQL timeout
max result rows
maximum top_k

Do not build an elaborate security framework.

Agent layer

Do not implement a custom agent reasoning loop unless there is a strong technical reason.

Use OpenCode as the agent harness.

The backend should invoke OpenCode programmatically/headlessly with:

user question
relevant conversation history
agent/system instructions
access to the MCP tools
selected LLM

The agent should be responsible for deciding:

which tool to use
whether another search is needed
whether results are sufficient
how to combine evidence
how to formulate the final answer

The runtime agent should not have arbitrary access to:

shell
filesystem
unrestricted HTTP
database credentials
repository editing

It should primarily have access to the MCP tools.

The eventual deployed agent environment should be isolated and read-only with respect to business data.

Backend

Build a small backend API.

Do not turn this into a large application framework.

Responsibilities:

receive user messages
maintain/pass conversation history
invoke the agent
stream or return the answer
expose minimal health/status endpoints if useful

A single endpoint such as:

POST /api/chat

is enough initially.

Example request:

{
  "message": "What is blocking deal D001?"
}

Conversation/session handling can stay simple.

Do not implement accounts, OAuth, RBAC, billing, etc.

Repository organization

Investigate the current repository first.

Do not blindly impose this exact structure, but aim toward boundaries similar to:

Reuse and move existing code rather than copying it into new implementations.

Avoid creating dozens of tiny files/classes merely for architectural purity.

Testing philosophy

Tests should protect important behavior, not maximize test count or coverage percentage.

Do not create large quantities of trivial unit tests.

Do not mock every internal function.

Do not spend more development time writing tests than implementing the feature.

Prioritize a few high-value tests.

Examples:

Retrieval smoke tests

Known query:

SSO data residency

should retrieve the expected transcript.

Known semantic query should retrieve a plausible expected transcript.

KG safety test

Verify that:

SELECT

works and destructive SPARQL is rejected.

MCP integration smoke test

Call each MCP tool once and verify that a valid structured response is returned.

End-to-end QA smoke test

One known question such as:

For D001, what is the current deal stage and value,
and what blockers could prevent it from closing?

should produce an answer combining CRM/KG information and transcript-derived evidence.

That level of testing is sufficient initially.

Add further tests only when they protect something likely to regress.

Milestones

Propose the implementation milestones described below, adjusted according to what actually exists in the repository.

STOP after producing this plan.

Milestone philosophy

Changes must be incremental and reviewable.

A milestone should ideally be something that can be understood from a relatively small diff.

Avoid a milestone such as:

Refactor entire repository and implement new architecture.

Prefer milestones such as:

Milestone 1 — repository cleanup

Goal:

establish clean package structure
move existing working retrieval code
centralize configuration
preserve existing behavior

No new functionality unless necessary.

Review before continuing.

Milestone 2 — retrieval service layer

Create clean Python interfaces around:

GraphDB
Chroma
BM25
transcript retrieval

Reuse existing implementations.

Verify each one independently.

Review before continuing.

Milestone 3 — MCP server

Expose the retrieval services through MCP.

Implement only the small initial tool set.

Verify tool calls manually / with minimal smoke tests.

Review before continuing.

Milestone 4 — agent integration

Configure OpenCode to use the MCP server.

Demonstrate several questions where the agent chooses different retrieval strategies.

Do not build UI yet.

Review before continuing.

Milestone 5 — backend

Add the minimal chat backend around the agent.

Verify one end-to-end API call.

Review before continuing.

Milestone 6 — UI

Build the minimal chat UI.

Connect it to the backend.

Review before continuing.

Milestone 7 — ingestion cleanup

Consolidate the currently separate ingestion scripts into a clear ingestion workflow.

Do not redesign working extraction logic unnecessarily.

Review before continuing.

Milestone 8 — end-to-end cleanup

Only after everything works:

remove clearly obsolete scripts
improve README
document startup / ingestion / QA
add any missing high-value smoke tests
Rules while implementing

For every milestone:

Explain what you intend to change.
Keep the change reasonably small.
Reuse existing code whenever practical.
Do not refactor unrelated code.
Run only relevant tests/checks.
Summarize:
files changed
behavior changed
tests/checks performed
known limitations
Stop and wait for review before beginning the next milestone.

Do not silently continue through all milestones.
